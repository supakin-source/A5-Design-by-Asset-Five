# A5 Design by Asset Five — LINE OA Chatbot

แชทบอท LINE Official Account สำหรับ **A5 Design by Asset Five** (บริษัทรับออกแบบและ
ก่อสร้างแบบ turn-key) ทำหน้าที่รับลูกค้าตลอด 24 ชม. โดยมีเป้าหมาย 2 ข้อ:

1. **สนทนากับลูกค้าและส่งต่อข้อมูลให้ผู้รับผิดชอบ** — บอทเก็บข้อมูลสำคัญ (ชื่อ,
   เบอร์ติดต่อ, ประเภทงาน, งบประมาณ, ทำเล, กรอบเวลา) แล้วแจ้งเตือนเข้ากลุ่ม LINE
   ของทีมงานพร้อมบันทึกลงฐานข้อมูล เพื่อให้ทีมงานติดต่อกลับได้ต่อเนื่อง
2. **แปลงบทสนทนาเป็น market data** — จัดหมวดหัวข้อที่ลูกค้าถาม ความรู้สึกในบทสนทนา
   ประเภทงาน/งบประมาณ/ทำเลที่ลูกค้าสนใจ แสดงเป็น dashboard สำหรับใช้ปรับปรุงบริการ
   และวางกลยุทธ์การตลาด

บอทถูกออกแบบให้ทำหน้าที่เหมือน **พนักงานต้อนรับ/คัดกรองเบื้องต้น** (คล้ายพยาบาลที่
ซักอาการก่อนส่งพบแพทย์) ไม่ใช่ผู้เชี่ยวชาญที่ตัดสินใจแทนบริษัท — รายละเอียดขอบเขต
และการควบคุมความเสี่ยงอยู่ใน [`docs/AI_POLICY.md`](docs/AI_POLICY.md) **กรุณาอ่าน
เอกสารนี้ก่อนเปิดใช้งานจริง**

## สถาปัตยกรรม

```
ลูกค้า (LINE) ──► LINE Messaging API ──► /api/line/webhook (Next.js บน Vercel)
                                              │
                          ┌───────────────────┼────────────────────┐
                          ▼                   ▼                    ▼
                 Gemini (ข้อความ+รูป)   Postgres (lead/       LINE push
                 ตอบ + สกัดข้อมูล        บทสนทนา/market data)  แจ้งทีมงาน
                                              │
                                              ▼
                                    /dashboard (ทีมงานภายใน)
```

- **Next.js 16 (App Router) + TypeScript** — รวม webhook และ dashboard ในโปรเจกต์เดียว
  deploy บน Vercel ได้ฟรี
- **Google Gemini** (`gemini-3.1-flash-lite` โดยค่าเริ่มต้น) — รองรับทั้งข้อความและรูปภาพ
  (อ่านข้อความในรูป/สรุปภาพหน้างาน) ในคำขอเดียว ไม่ต้องต่อ OCR แยก และมี free tier
  ที่เพียงพอกับปริมาณลูกค้าระดับไม่เกิน ~20 คน/วัน
- **Prisma + PostgreSQL** — เก็บ lead, บทสนทนา และข้อมูลเชิงหมวดหมู่สำหรับวิเคราะห์
- **Recharts** — กราฟในหน้า Market data

## ขั้นตอนติดตั้ง

### 1) เตรียม LINE Official Account

1. สร้าง Provider และ **Messaging API channel** ที่ https://developers.line.biz/console/

   > ⚠️ **สำคัญถ้าคิดจะใช้ LIFF ในอนาคต**: ให้สร้าง channel ทุกตัวของโปรเจกต์นี้ไว้ใต้
   > **Provider เดียวกัน** เพราะ LIFF ต้องอยู่ใต้ LINE Login channel แยกอีกตัว และจะ
   > เชื่อมกับ LINE OA (Linked LINE Official Account) ได้เฉพาะเมื่ออยู่ Provider เดียวกัน
   > — ถ้าสร้างคนละ Provider ภายหลังย้ายไม่ได้ ต้องสร้างใหม่ทั้งชุด

2. ในแท็บ **Messaging API** กด Issue สำหรับ `Channel access token` (long-lived)
3. ในแท็บ **Basic settings** คัดลอก `Channel secret`
4. ปิด **Auto-reply messages** และ **Greeting messages** ของ LINE OA
   (ที่ https://manager.line.biz) เพื่อไม่ให้ตอบซ้อนกับบอท

> 🛑 **ยังไม่ต้องตั้งค่า Webhook ในขั้นตอนนี้** — ช่อง "ลิงก์ Webhook" ต้องใช้ URL ของ
> ระบบที่ deploy แล้ว ซึ่งจะได้ในขั้นตอนที่ 6 ให้ปล่อยว่างไว้ก่อนแล้วกลับมาทำทีหลัง
> (จะตั้งจาก LINE Developers Console หรือจาก LINE OA Manager → การตั้งค่า →
> Messaging API ก็ได้ ทั้งสองที่คือค่าเดียวกัน)

### 2) ขอ Gemini API key

สร้าง API key ฟรีที่ https://aistudio.google.com/app/apikey (ตรวจสอบ rate limit ของ
free tier ให้สอดคล้องกับปริมาณลูกค้าที่คาดการณ์)

### 3) เตรียมฐานข้อมูล PostgreSQL

ใช้บริการที่มี free tier ได้ เช่น Neon (https://neon.tech) หรือ Supabase
(https://supabase.com) แล้วคัดลอก connection string มาใส่ `DATABASE_URL`

### 4) ตั้งค่า environment variables

คัดลอก `.env.example` เป็น `.env.local` แล้วกรอกค่าให้ครบ

| ตัวแปร | คำอธิบาย |
| --- | --- |
| `LINE_CHANNEL_ACCESS_TOKEN` | Channel access token จาก LINE Developers |
| `LINE_CHANNEL_SECRET` | Channel secret (ใช้ตรวจลายเซ็น webhook) |
| `LINE_STAFF_NOTIFY_ID` | user ID หรือ group ID ที่จะรับแจ้งเตือนลูกค้าใหม่ |
| `GEMINI_API_KEY` | API key จาก Google AI Studio |
| `GEMINI_MODEL` | รุ่นหลัก ค่าเริ่มต้น `gemini-3.1-flash-lite` |
| `GEMINI_FALLBACK_MODEL` | รุ่นสำรองเมื่อรุ่นหลักโควตาหมด **ปิดไว้โดยค่าเริ่มต้น** ใส่ชื่อรุ่นอื่นเพื่อเปิด (ได้โควตาอีกก้อน) |
| `DATABASE_URL` | connection string ของ PostgreSQL |
| `DASHBOARD_USERNAME` / `DASHBOARD_PASSWORD` | บัญชีเข้า dashboard ของทีมงาน |
| `SESSION_SECRET` | สตริงสุ่มยาว ๆ ใช้เซ็น session cookie |
| `DASHBOARD_ADMIN_PASSWORD` | รหัสผ่านชั้นที่สอง ต้องกรอกก่อนยืนยันการแก้ไข/ลบ/merge ข้อมูลลูกค้าใน dashboard (แยกจาก `DASHBOARD_PASSWORD` ที่ใช้ล็อกอิน) |

> **การหา `LINE_STAFF_NOTIFY_ID` ของกลุ่ม**: เชิญ LINE OA เข้ากลุ่มของทีมงาน แล้วส่ง
> ข้อความในกลุ่มหนึ่งครั้ง จากนั้นดู log ของ webhook (Vercel → Logs) จะเห็น
> `source.groupId` ให้นำค่านั้นมาใส่ (ถ้าต้องการแจ้งเข้าบุคคล ให้ใช้ `source.userId`)

### 5) รันในเครื่อง

```bash
npm install
npx prisma migrate deploy   # หรือ npx prisma migrate dev ตอนพัฒนา
npm run db:seed             # (ไม่บังคับ) ใส่ข้อมูลตัวอย่างเพื่อดู dashboard
npm run dev                 # http://localhost:3000
```

### 6) Deploy บน Vercel และตั้ง webhook

1. Import repo นี้เข้า Vercel และใส่ environment variables ทั้งหมดข้างต้น

   > ตรวจว่า **Framework Preset** เป็น `Next.js` (ไม่ใช่ `Other`) ไม่งั้น build จะสำเร็จ
   > แต่ deploy fail ด้วยข้อความ `No Output Directory named "public" found`
   > โปรเจกต์มี `vercel.json` ระบุ `"framework": "nextjs"` ไว้แล้ว แต่ถ้าค่าใน
   > dashboard ถูกตั้งเป็น Other ไว้ก่อนหน้า ให้แก้ที่ Settings → Build and Deployment
2. กด Deploy — สคริปต์ `build` จะรัน `prisma migrate deploy` ให้อัตโนมัติ จึงสร้าง
   ตารางในฐานข้อมูลเองโดยไม่ต้องรันคำสั่งในเครื่อง (ถ้าต้องการรันมือ ใช้
   `npx prisma migrate deploy` โดยตั้ง `DATABASE_URL` ของ production)

   > หมายเหตุ: preview deployment ของ Vercel ก็จะรัน migration กับฐานข้อมูลที่ตั้งไว้
   > ใน env เดียวกัน ถ้าในอนาคตต้องการแยกฐานข้อมูล production/preview ให้ตั้งค่า
   > `DATABASE_URL` แยกตาม environment ใน Vercel
3. กลับไปที่การตั้งค่า LINE (ขั้นตอนที่ 1) นำ URL
   `https://<โดเมนของคุณ>/api/line/webhook` ใส่ในช่อง **Webhook URL / ลิงก์ Webhook**
   → บันทึก → เปิด **Use webhook** ให้เป็น ON → กด **Verify**

   ต้องใส่ `LINE_CHANNEL_SECRET` ใน Vercel ให้ถูกต้องก่อนกด Verify เพราะ LINE จะส่ง
   request ที่มีลายเซ็นมาทดสอบ ถ้า secret ไม่ตรง ระบบจะตอบ 401 และ Verify จะไม่ผ่าน
   (เป็นการทำงานที่ถูกต้อง ไม่ใช่ข้อผิดพลาด)

## การใช้งาน dashboard

เข้า `/dashboard` (ต้องล็อกอินด้วย `DASHBOARD_USERNAME`/`DASHBOARD_PASSWORD`)

- **ภาพรวม** — จำนวนลูกค้าทั้งหมด, รายใหม่ 7 วัน, จำนวนที่รอทีมงานติดต่อกลับ
- **รายชื่อลูกค้า** — ตารางลูกค้าพร้อมข้อมูลที่บอทเก็บได้ คลิกเพื่อดูบทสนทนาทั้งหมด
  และประวัติการแจ้งเตือนทีมงาน หน้ารายละเอียดแต่ละงานแสดงงานอื่น ๆ ของลูกค้ารายนั้นด้วย
  (ลูกค้าเดิมที่กลับมาขอรับบริการใหม่จะได้งานแยกต่างหาก ไม่ทับข้อมูลงานเดิม)
- **แก้ไข/ลบ/merge ข้อมูล** — ปุ่ม "แก้ไขข้อมูล" ในหน้ารายละเอียดแก้ไขทุกฟิลด์และสถานะได้
  ปุ่ม "ลบงานนี้ถาวร" ลบงานนั้นทั้งชุด (บทสนทนา, การแจ้งเตือน) และถ้าเจองานซ้ำซ้อนกัน
  (เช่นบอทสร้างงานใหม่ผิดพลาดกลางบทสนทนาเดียวกัน) ปุ่ม "merge เข้ากับงานนี้" ในตาราง
  ประวัติจะรวมงานซ้ำนั้นเข้ากับงานที่กำลังดูอยู่ — ทุกการแก้ไข/ลบ/merge ต้องกรอก
  `DASHBOARD_ADMIN_PASSWORD` ยืนยันก่อนเสมอ (แยกจากรหัสผ่านล็อกอิน dashboard)
- **Market data** — กราฟประเภทงาน/งบประมาณ/ทำเล, หัวข้อที่ลูกค้าถามบ่อย,
  ความรู้สึกในบทสนทนา และจำนวนลูกค้าใหม่รายวัน (ทุกกราฟสลับดูเป็นตารางได้)

## บุคลิกของบอท และการอ่านข้อความที่ส่งมาทีละท่อน

**บุคลิก (persona)** กำหนดไว้ที่ `PERSONA` ใน [`src/lib/policy.ts`](src/lib/policy.ts)
— ปัจจุบันคือ **"Ady"** ผู้ช่วย AI เพศหญิง โทนแบบ Gen Y สุภาพ นอบน้อม อ่อนหวาน
เป็นมิตร **ตอบด้วยภาษาเดียวกับที่ลูกค้าใช้** (ไทย/อังกฤษ/อื่น ๆ) ตอบสั้น 1-3 ประโยค
และถามอย่างมีชั้นเชิงเพื่อให้ได้ข้อมูลมากโดยลูกค้าไม่อึดอัด (ปลายเปิดก่อนเจาะลึก,
ทวนสิ่งที่ลูกค้าเล่า, เสนอตัวเลือกเมื่อลังเล, ไม่คะยั้นคะยอถ้าลูกค้าเลี่ยง)
คำตอบถูกแบ่งเป็น **ฟองแชทสั้น 1-3 ฟอง** (ปกติ 2 ฟอง: ฟองแรกตอบ ฟองท้ายถามต่อ)
ส่งออกในการเรียก reply ครั้งเดียวจึงไม่กินโควตา push ของ LINE และระบบมีตัวกันไว้
อีกชั้น (`normalizeBubbles`) ที่ตัดฟองว่าง จำกัดไม่เกิน 3 ฟอง และหั่นฟองที่ยาวเกิน
ที่ช่องว่างแทนกลางคำ
รายละเอียดทั้งหมดอยู่ใน [`docs/AI_POLICY.md`](docs/AI_POLICY.md) §1.1 —
เปลี่ยนชื่อ/เพศ/คำลงท้ายได้ที่จุดเดียวแล้วมีผลทั้งระบบรวมถึงข้อความทักทาย

**การรวมข้อความที่ส่งมาทีละท่อน** ลูกค้ามักพิมพ์แยกเป็นท่อน เช่น "สวัสดี" →
"อยากติดต่อเรื่อง" → "การต่อเติม" ถ้าตอบทีละท่อนบอทจะตอบ 3 ครั้งแบบไม่เข้าใจบริบท
และเปลืองโควตา AI 3 เท่า ระบบจึงทำงานแบบนี้:

1. ข้อความที่เข้ามาถูกพักไว้ในคิว (`PendingMessage`) แล้วตอบ 200 ให้ LINE ทันที
   (~0.02 วินาที) จึงไม่มีปัญหา timeout
2. รอ `MESSAGE_DEBOUNCE_MS` (ค่าเริ่มต้น **8 วินาที**) หากลูกค้าพิมพ์ต่อ ตัวจับเวลา
   จะเริ่มนับใหม่จากข้อความล่าสุด
3. เมื่อครบเวลา ทุกท่อนจะถูกรวมเป็นข้อความเดียว ส่งให้ AI **อ่านทีเดียวตอบครั้งเดียว**
   โดยใช้ reply token ของข้อความล่าสุด (ไม่กินโควตา push message ของ LINE)
4. ประวัติแชทใน dashboard ยังเก็บแยกทีละท่อนตามที่ลูกค้าพิมพ์จริง

> ⚠️ **ข้อจำกัดที่ต้องรู้:** เวลารอทั้งหมด + เวลาเรียก AI ต้องไม่เกินเพดาน function
> ของแพ็กเกจ hosting (ตั้ง `maxDuration = 60` ไว้ในไฟล์ webhook แต่แพ็กเกจอาจจำกัด
> ต่ำกว่านั้น) ถ้าพบว่าบอทเงียบไม่ตอบและ log ขึ้น timeout ให้ลดค่า
> `MESSAGE_DEBOUNCE_MS` (เช่น 4000) แล้ว redeploy — ไม่ต้องแก้โค้ด
>
> ถ้า function ถูกตัดจบกลางทาง ข้อความที่ค้างในคิวจะไม่หาย และจะถูกรวมไปตอบพร้อม
> ข้อความถัดไปที่ลูกค้าส่งมา

## การทดสอบบทสนทนา (ไม่ต้องนั่งแชทเอง)

มี AI สวมบทเป็นลูกค้าหลายแบบมาคุยกับบอทจริง (ใช้ prompt/persona/นโยบายชุดเดียวกับ
production) แล้วตรวจกฎอัตโนมัติทุกคำตอบ

**วิธีที่ง่ายที่สุด — รันบน GitHub ไม่ต้องใช้เครื่องตัวเอง**

1. ใส่ API key ครั้งเดียว: repo → **Settings → Secrets and variables → Actions →
   New repository secret** ชื่อ `GEMINI_API_KEY`
2. ไปแท็บ **Actions → Chat test → Run workflow** แล้วกรอกช่องที่ต้องการ
   - **model** — โมเดลที่จะทดสอบ เช่น `gemini-3.1-flash-lite` (เว้นว่าง = ใช้ค่าเริ่มต้น)
     ใช้ช่องนี้เปรียบเทียบคุณภาพระหว่างรุ่นก่อนตัดสินใจเปลี่ยนใน production ได้
   - **scenario** — ชื่อบางส่วนของ scenario ที่ต้องการรัน (เว้นว่าง = รันทั้งหมด)
   - **ai_customer** — ให้ AI ด้นบทลูกค้าเอง (ใช้โควตาเกือบสองเท่า)
3. อ่านบทสนทนาและผลตรวจใน log ของ run นั้น

**หรือรันในเครื่อง**

```bash
GEMINI_API_KEY=xxx npm run test:chat                  # รันทุก scenario
GEMINI_API_KEY=xxx npm run test:chat -- ราคา          # เฉพาะ scenario ที่ชื่อมีคำว่า "ราคา"
GEMINI_API_KEY=xxx npm run test:chat -- --budget=6    # หยุดเองเมื่อใช้ครบ 6 request
GEMINI_MODEL=gemini-3.1-flash-lite npm run test:chat  # ทดสอบรุ่นอื่น
```

แต่ละ scenario มี **ชุดคำถาม 3 ชุดในบริบทเดียวกัน** และสลับชุดทุกรอบ เพื่อวัดว่ากฎยัง
อยู่เมื่อคำถามถูกเปลี่ยนสำนวน ไม่ใช่แค่จำคำตอบเดิมได้

### ⚠️ โควตา Gemini ที่ต้องระวังเวลาเทส

บทสนทนา 1 ตาของบอท = **1 Gemini request** และใช้โควตา**ก้อนเดียวกับบอทตัวจริง**
ถ้าเทสจนโควตาหมด ลูกค้าจริงจะได้ข้อความสำรองจนกว่าโควตาจะรีเซ็ต

- **มี 2 ลิมิตแยกกัน**: ต่อนาที (RPM) และต่อวัน (RPD) ชนอันไหนก็ถูกปฏิเสธเหมือนกัน
  สคริปต์จึงเว้นจังหวะระหว่าง request (ค่าเริ่มต้น 5 วินาที ปรับด้วย `--gap=`) และถ้า
  โดนปฏิเสธจะรอตามเวลาที่ API แนะนำแล้วลองใหม่หนึ่งครั้ง ก่อนสรุปว่าโควตารายวันหมดจริง
- รันทุก scenario ≈ 15 request · รันทีละอันประมาณ 2-4 request
- สคริปต์จะแจ้งจำนวน request ที่จะใช้ก่อนเริ่ม และรายงานยอดที่ใช้จริงตอนจบ
- ถ้าโควตาหมดกลางคัน จะหยุดพร้อมบอกว่าใช้ไปเท่าไหร่และให้ลองใหม่เมื่อไหร่ (exit code 3)
  แทนที่จะพ่น stack trace
- ตรวจโควตาจริงของ key ตัวเองได้ที่ https://ai.dev/rate-limit (แต่ละรุ่นไม่เท่ากัน)

**แนะนำ:** ทดสอบด้วยการรันทีละ scenario
`npm run test:chat -- ราคา` แล้วค่อยขยับไปทีละอัน

### โหมดรันยาว (soak test)

รันวนซ้ำหลายรอบเป็นเวลานาน เพื่อดูว่าโมเดล **ทำตามกฎได้สม่ำเสมอ** หรือผ่านบ้าง
ไม่ผ่านบ้าง — สำคัญกับรุ่นเล็กที่คำตอบแกว่งกว่า

```bash
npm run test:chat -- --duration=2h --budget=60
```

- `--duration` รับ `2h`, `90m`, `3600s`
- `--budget` เพดาน request ทั้งรัน **ควรใส่เสมอในโหมดนี้** สคริปต์จะกระจายจังหวะ
  ให้เอง (2 ชม. / 60 request = ยิงทุก 2 นาที) กันทั้ง rate limit ต่อนาทีและโควตารายวัน
- ถ้าไม่ใส่ `--budget` และแผนจะใช้เกิน ~200 request สคริปต์จะเตือนก่อน

ผลสรุปตอนจบจะบอก **อัตราการผ่านของแต่ละ scenario** และนับว่าผิดกฎข้อไหนกี่ครั้ง เช่น

```
  ⚠️  คะยั้นคะยอถามราคา — ผ่าน 7/10 (70%)
        ผิดกฎ [price-quote] 3 ครั้ง
```

รันบน GitHub Actions ได้เช่นกัน (ช่อง duration/budget ในหน้า Run workflow) แต่ระวัง
โควตา Actions: รัน 2 ชม. = ใช้ 120 นาทีจากโควตาฟรี 2,000 นาที/เดือนของ repo แบบ private

> เคยลองตั้ง `schedule:` ให้รันเองทุกวันตอนเที่ยง แต่ GitHub ไม่ยิงให้เลยแม้รอเกิน
> 2 ชม. (0 run จาก event `schedule` — ตรวจสอบผ่าน Actions API) คาดว่าเพราะตั้งเวลาไว้
> ตรงต้นชั่วโมงพอดี (`0 5 * * *`) ซึ่งเป็นช่วงที่คิวงาน cron ทั่วโลกแน่นที่สุดจนอาจถูก
> ข้ามไปเลย ไม่ใช่แค่ดีเลย์ จึงตัด schedule ออกแล้ว — ให้กด **Run workflow** เองตอน
> ต้องการทดสอบยาว ๆ แทน

## บอทไม่ตอบทุกข้อความ (ประหยัดโควตา + เป็นธรรมชาติกว่า)

พนักงานต้อนรับที่ดีไม่พูดตอบทุกคำ ระบบจึงกรอง 2 ชั้น:

**ชั้นที่ 1 — กรองในโค้ดก่อนเรียก AI** ([`src/lib/acknowledgement.ts`](src/lib/acknowledgement.ts))
ข้อความปิดบทสนทนาล้วน ๆ ("ขอบคุณครับ", "โอเค", "จ้า", "thanks", "รับทราบ", อีโมจิ
ล้วน) จะ **ไม่ถูกส่งไปหา AI เลย** ประหยัด 1 request เต็ม ๆ ต่อข้อความ ระบบยังบันทึก
ข้อความนั้นไว้ใน market data (topic = "รับทราบ/ปิดบทสนทนา") แต่ไม่ตอบกลับ

ตัวกรองตั้งใจให้ระแวดระวัง — ถ้าข้อความมีคำถาม มีตัวเลข (เบอร์/งบ/พื้นที่) หรือมี
เนื้อความอื่นปนมา จะไม่ถือเป็นคำปิด เช่น "ขอบคุณครับ **แล้วราคาล่ะ**" ยังได้คำตอบปกติ

**ชั้นที่ 2 — ให้ AI ตัดสินใจเงียบเอง** (ฟิลด์ `shouldReply`)
สำหรับเคสที่ต้องใช้วิจารณญาณ เช่น ลูกค้าคุยนอกเรื่องซ้ำหลังจากบอทชี้กลับเข้าเรื่อง
ไปแล้วหนึ่งครั้ง หรือข้อความที่ไม่ได้สื่อสารกับเรา

กฎที่เขียนไว้ชัดว่า **ห้ามเงียบเด็ดขาด** เมื่อ: ลูกค้าถามคำถาม, ให้ข้อมูลใหม่
(เบอร์/งบ/พื้นที่/ประเภทงาน), ขอคุยกับคน, ร้องเรียน, หรือเป็นข้อความแรกของบทสนทนา —
และเมื่อไม่แน่ใจให้ตอบไว้ก่อนเสมอ

## หมวดหมู่สำหรับ market data

`topic`, `projectType` และ `budgetRange` **บังคับให้เลือกจากรายการที่กำหนด** ใน
[`src/lib/policy.ts`](src/lib/policy.ts) (`TOPICS`, `PROJECT_TYPES`, `BUDGET_BANDS`)
เพราะตอนปล่อยให้โมเดลตั้งชื่อเอง เรื่องเดียวกันถูกนับแยกกันเป็น `inquiry_price` /
`ราคาค่าก่อสร้าง` / `pricing` และงบ "3 แสน" กับ "300,000" กลายเป็นคนละแท่ง ทำให้กราฟ
ใน dashboard ใช้วิเคราะห์ไม่ได้

รายละเอียดตามคำพูดลูกค้า (เช่น "ต่อเติมครัวหลังบ้าน 20 ตร.ม.") เก็บแยกไว้ในช่อง
`projectDetail` ซึ่งแสดงในหน้ารายชื่อลูกค้าและส่งไปในข้อความแจ้งเตือนทีมงานด้วย —
หมวดหมู่ไว้ทำกราฟ รายละเอียดไว้ให้คนอ่าน

แก้รายการเหล่านี้ได้ตามที่ธุรกิจต้องการ แต่ถ้าเปลี่ยนหลังเก็บข้อมูลไปแล้ว ค่าเก่าใน
ฐานข้อมูลจะยังเป็นชื่อเดิม (กราฟจะมีทั้งชื่อเก่าและใหม่จนกว่าจะแก้ข้อมูลย้อนหลัง)

## ล้างข้อมูลทดสอบก่อนเปิดใช้จริง

ข้อมูลจากการทดสอบใช้หมวดหมู่ชุดเก่า ถ้าปล่อยไว้จะปนกับข้อมูลลูกค้าจริงในกราฟ

```bash
npm run db:reset-test                    # dry run — บอกจำนวนที่จะลบ ยังไม่ลบ
npm run db:reset-test -- --yes           # ลบจริง
npm run db:reset-test -- --yes --before=2026-09-02   # ลบเฉพาะที่เก่ากว่าวันที่กำหนด
```

ลบ Lead, Project, Conversation, Message, StaffNotification และคิวข้อความค้างไปพร้อมกันทั้งชุด
(ถ้าลบแยกจะเหลือ lead ที่ไม่มีบทสนทนา ซึ่งแย่กว่าไม่มีข้อมูลเลย)

รันกับฐานข้อมูล production ได้โดยตั้ง `DATABASE_URL` ให้ชี้ไปที่ Neon:
`DATABASE_URL="postgresql://..." npm run db:reset-test`

## รวมข้อมูลงานที่ซ้ำซ้อนกัน (duplicate projects)

ถ้าเจองานซ้ำซ้อนของลูกค้าคนเดียวกันที่ควรเป็นงานเดียว (เช่นจากบั๊กที่บอทสร้างงานใหม่
กลางบทสนทนาเดียวกัน) ใช้ปุ่ม "merge เข้ากับงานนี้" ในหน้ารายละเอียดลูกค้าบน dashboard
ได้เลย หรือรันจากเทอร์มินัลก็ได้:

```bash
npx tsx scripts/merge-duplicate-projects.ts <primaryProjectId> <duplicateProjectId...>            # dry run
npx tsx scripts/merge-duplicate-projects.ts <primaryProjectId> <duplicateProjectId...> --yes       # merge จริง
```

ย้ายบทสนทนาและการแจ้งเตือนทั้งหมดจากงานที่ซ้ำไปไว้ที่งานหลัก เติมฟิลด์ที่งานหลัก
ยังไม่มีจากงานที่ซ้ำ แล้วลบงานที่ซ้ำทิ้ง ปฏิเสธการ merge ถ้างานทั้งสองเป็นของลูกค้าคนละคน

## การปรับแต่งขอบเขตคำตอบของบอท

ฐานความรู้และกฎการตอบอยู่ที่ [`src/lib/policy.ts`](src/lib/policy.ts)

- ปัจจุบันบรรจุข้อมูลแบรนด์จริงของ A5 แล้ว (อัตลักษณ์ "A5 GREATNESS Inspired by
  Love", ปรัชญา Emerald Cut, 3 เสาหลัก Nature/Well-being/Sustainability, เป้าหมาย
  ความยั่งยืน และโครงการในเครือ) — ที่ยังขาดและบอทจะตอบว่า "ยังไม่มีข้อมูล" คือ
  พื้นที่ให้บริการ, ขั้นตอน/ระยะเวลาแต่ละเฟส, เงื่อนไขรับประกัน และช่องทางติดต่ออื่น
- **ข้อมูลเชิงธุรกิจภายในถูกกันออกโดยตั้งใจ** (เป้ายอดขาย, backlog, pipeline,
  แผนการเงิน, แผน ESG rating) เพราะแชทเปิดให้ใครก็เข้ามาถามได้ รวมถึงคู่แข่ง —
  และมีกฎห้ามบอทพูดถึงแม้ถูกถามตรง ๆ
- บอทถูกกำหนดให้ตอบได้เฉพาะสิ่งที่อยู่ในฐานความรู้นี้ หากไม่มีข้อมูลจะตอบว่ายังไม่มี
  ข้อมูลและส่งต่อทีมงาน — **ห้ามเสนอราคาหรือรับปากระยะเวลา/เงื่อนไขสัญญา**
- หากต้องการให้บอทตอบเรื่องใหม่ ให้เพิ่มเนื้อหาในฐานความรู้ ไม่ใช่แก้กฎให้ตอบได้
  ทุกอย่าง

## โควตา Gemini และรุ่นสำรอง

Free tier จำกัดจำนวน request **ต่อวัน แยกตามรุ่น** (เช่นที่พบจริง: `gemini-3.5-flash`
ได้ 20 request/วัน) 1 ตาสนทนาของบอท = 1 request ดังนั้นโควตา 20 = รับลูกค้าได้เพียง
~5 คน/วัน

ระบบจึงตั้งไว้ 2 รุ่น: เรียก `GEMINI_MODEL` ก่อน ถ้าโดนปฏิเสธเพราะโควตาหมด (429)
จะลองใหม่ด้วย `GEMINI_FALLBACK_MODEL` ทันที **ซึ่งมีโควตาก้อนของตัวเอง** ทำให้บอท
ยังคุยต่อได้แทนที่จะเงียบทั้งวัน ถ้าหมดทั้งสองรุ่นจึงจะตอบข้อความสำรองและส่งต่อทีมงาน

ดูโควตาจริงของ key ตัวเองได้ที่ https://ai.dev/rate-limit — ถ้าปริมาณลูกค้าจริงเกิน
โควตาฟรีเป็นประจำ ควรเปิด billing เพราะการที่บอทเงียบกลางวันเสียหายกว่าค่า API

## ⚠️ การปลดระวางรุ่นของ Gemini (ต้องตรวจเป็นระยะ)

Google ทยอยปิดให้บริการ model รุ่นเก่าตามกำหนด เช่น `gemini-2.0-flash` ถูกปิดไปแล้ว
เมื่อ 1 มิถุนายน 2026 **เมื่อรุ่นที่ใช้อยู่ถูกปิด บอทจะไม่ตอบด้วย AI อีก** แต่จะตอบ
ข้อความสำรองและส่งต่อทีมงานทุกครั้ง (เห็น `[gemini] falling back to human handoff`
พร้อม error 404 ใน log ของ Vercel)

วิธีแก้เมื่อเกิดเหตุนี้: ตรวจรายชื่อรุ่นที่ใช้ได้ปัจจุบัน แล้วแก้ค่า `GEMINI_MODEL`
ใน Vercel → Redeploy (ไม่ต้องแก้โค้ด)

ตรวจรายชื่อรุ่นที่ key ของคุณใช้ได้:
`https://generativelanguage.googleapis.com/v1beta/models?key=<GEMINI_API_KEY>`

## พฤติกรรมเมื่อระบบ AI ใช้งานไม่ได้

หาก Gemini ใช้โควตาหมดหรือขัดข้อง บอทจะไม่ปล่อยลูกค้าค้าง แต่จะตอบข้อความแจ้งว่า
ทีมงานจะติดต่อกลับ พร้อมส่งต่อเคสให้ทีมงานทันที (สถานะ `ai_unavailable`) และการ
แจ้งเตือนที่ส่งไม่สำเร็จจะถูกบันทึกไว้ให้เห็นใน dashboard ไม่หายไปเงียบ ๆ

## หมายเหตุด้าน PDPA

- ข้อความแรกที่บอทคุยกับลูกค้าใหม่จะแจ้งวัตถุประสงค์การเก็บข้อมูล และระบบบันทึก
  เวลาที่แจ้ง (`consentShownAt`)
- รูปภาพที่ลูกค้าส่งมาจะไม่ถูกเก็บเป็นไฟล์ในระบบ เก็บเพียงคำอธิบายสรุปที่จำเป็นต่อ
  การส่งต่องาน
- ผู้เข้าถึง dashboard ต้องรักษาความลับข้อมูลลูกค้าตามนโยบายบริษัทและ PDPA

  channel เพิ่ม — ชนิดข้อมูลใน [`src/lib/line.ts`](src/lib/line.ts) (`LineMessage`,
  `LineQuickReply`, `LineAction`) รองรับไว้แล้ว ส่งได้ผ่าน `replyMessage`/`pushMessage`
  เดิมโดยไม่ต้องแก้ตัวส่ง เหมาะกับปุ่มเลือกประเภทงาน/ช่วงงบประมาณ ซึ่งได้ข้อมูลแม่นยำ
  กว่าและช่วยประหยัดโควตา AI
- **Rich Menu** (เมนูค้างล่างหน้าแชท) ตั้งได้จาก LINE Manager โดยไม่ต้องเขียนโค้ด
- **LIFF** (เว็บฟอร์มในแอป LINE) ต้องสร้าง **LINE Login channel** เพิ่มใต้ Provider
  เดียวกัน แล้วลงทะเบียน LIFF app — เหมาะกับฟอร์มกรอกรายละเอียดโครงการแบบมีโครงสร้าง
  หรือจองนัดดูหน้างาน

## สิ่งที่ยังไม่ได้ทำ (ข้อเสนอถัดไป)

- ยังไม่มีปุ่ม/เมนู Quick Reply สำหรับเก็บข้อมูลแบบมีโครงสร้าง (ช่วยลดการใช้โควตา AI
  และเพิ่มความแม่นยำได้ หากปริมาณลูกค้าเพิ่มขึ้น)
- ยังไม่มีฟังก์ชันให้ทีมงานอัปเดตสถานะ/บันทึกโน้ตลูกค้าจาก dashboard (ตอนนี้อ่านได้
  เท่านั้น)
- ยังไม่มีการ export market data เป็น CSV/Excel และยังไม่มีระบบผู้ใช้หลายบัญชี
